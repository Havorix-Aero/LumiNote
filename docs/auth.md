# 鉴权与恢复流程

## 口令

- 使用 **PBKDF2-SHA256**（WebCrypto，无第三方依赖），每用户独立 128-bit 盐，默认 100,000 次迭代。
- 100,000 是 Cloudflare Workers 运行时的上限：`crypto.subtle.deriveBits` 超出该值会直接报错（`iteration counts above 100000 are not supported`）。本地 `workerd` 不会拦，所以调高这个值只会在部署后才暴露问题——`packages/worker/test/auth.test.ts` 里有一条断言守住这个上限。
- 迭代次数、哈希算法、盐长度都随凭据一起存储在 `credentials.params_json` 中，因此将来可以提升强度：旧哈希仍可验证，并在下一次成功登录时透明地重新哈希（`needsRehash`）。
- 用户名不存在时也会执行一次 PBKDF2 计算，避免通过响应时间区分“用户不存在”和“密码错误”。

## 两步验证（TOTP）

- 遵循 RFC 6238：6 位、30 秒、允许前后 1 个时间窗。
- 密钥从不在数据库中明文保存：使用 `TOTP_MASTER_KEY`（32 字节 AES-GCM 密钥）加密后存入 `totp.secret_enc`。
- 启用需要先验证一次动态码（确认用户已成功绑定），随后生成 10 个一次性备用码（哈希存储）。

## 设备

- 设备 Cookie 是 `<deviceId>.<secret>`；数据库只保存 `secret` 的带盐哈希。
- 设备只有在通过完整 2FA（或完成恢复后的重设）之后才会被标记为 `trusted`。
- 受信任设备登录时跳过 2FA；未受信任设备必须通过 2FA 或密保问题。

## 会话

- 256-bit 随机令牌，只保存其 SHA-256（与 `SESSION_PEPPER` 混合，防止仅凭数据库泄露就能伪造）。
- Cookie：`httpOnly`、`Secure`、`SameSite=Lax`、`Path=/`；滑动 30 天，绝对上限 90 天。
- 滑动续期是惰性的（最多每小时写一次），避免每个请求都产生 D1 写入。
- 变更类请求需要同源校验 + 双提交 CSRF 令牌（Cookie 可被 JS 读取，但跨站攻击者无法设置自定义请求头）。
- 修改密码会撤销该账号的其它所有会话。

## 密保问题恢复

```
新设备登录
   │  密码正确 + 已开启 2FA + 设备未受信任
   ▼
two_fa_required（challengeToken，5 分钟）
   ├── 输入动态码 ──► 登录成功（可选择信任设备）
   └── 选择“用密保问题登录”
          ▼
   POST /auth/recovery/start
        · 随机挑一个**未被消耗**的问题（避免同一个问题反复被钓鱼）
        · 返回 recoveryToken（10 分钟）+ 问题文案
          ▼
   POST /auth/recovery/verify
        · 答案规范化（NFKC、去首尾空白、合并空格、小写）后 PBKDF2 比对
        · 最多 5 次尝试，超出即作废
        · 成功：消耗该问题、标记 must_reset_questions = 1、
          建立 scope = 'recovery' 的会话；该设备**不会**因此获得信任
          ▼
   受限会话（只能操作 /auth/password 与 /me/*）
        · 任何笔记 / 同步 / AI 请求都会返回 403 questions_reset_required
          ▼
   PUT /me/security-questions（必须重设全部 3 个问题）
        · 完成后清除 must_reset_questions，并把当前会话升级为 scope = 'full'
```

**为什么是“消费一个问题”**：密保问题是有限资源，被使用一次就必须作废，否则一次泄露可以被无限复用。强制重设全部问题保证账号在使用恢复通道后立即恢复到完整强度。

**为什么恢复会话默认受限**：仅凭一个密保答案不应获得完整的长期访问权。它只够用来“把账号修好”。

### 强制重设的作用范围

`mustResetQuestions` 是该账号的**全局**状态，不是单个会话的属性。因此：

- 触发恢复的设备会被挡住；
- 其它设备的下一次请求同样会被挡住，直到问题被重设。

这符合“下次登录时强制修改所有密保问题”的预期。

## 限流与审计

- 固定窗口计数器存在 D1（而不是 KV），因为限流必须强一致：攻击者不应能换个边缘节点重放同一批尝试。
- 登录同时按 IP 与按账号限流；2FA、恢复发起与恢复校验各自独立限流。
- 所有与安全相关的事件都写入 `audit_log`（注册、登录成功/失败、2FA 变更、恢复使用、设备撤销等），写入失败不会影响主流程。

## 密钥

| 名称              | 用途                                      |
| ----------------- | ----------------------------------------- |
| `SESSION_PEPPER`  | 与会话/设备令牌混合后再哈希               |
| `TOTP_MASTER_KEY` | 32 字节 base64url，AES-GCM 加密 TOTP 密钥 |

两者都通过 `wrangler secret put` 配置；未配置时接口会以明确的错误信息失败，而不是静默降级。
